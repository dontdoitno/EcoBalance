# ADR-0004: словарь вместо `next-intl` для единственной локали

- Статус: принято
- Дата: 2026-10-29

## Контекст

Исходное ТЗ требует, чтобы язык интерфейса был русским, а тексты не
хардкодились в компонентах («i18n-ready», со ссылкой на `next-intl`
как конкретный инструмент). На практике продукт сейчас имеет ровно
одну локаль.

## Решение

Все тексты UI вынесены в `apps/web/lib/dictionaries/ru.ts` — плоский
объект, импортируемый компонентами (`dict.wizard.calculate` и т.п.), не
встроенный в JSX напрямую. Полноценный `next-intl` runtime (провайдер,
middleware для определения локали, маршрутизация `/[locale]/...`) не
подключён.

## Почему не `next-intl`

Для одной локали `next-intl` добавляет runtime-накладные расходы
(контекст, форматтеры, middleware) без практической выгоды — выгода
появляется только при реальном переключении языков. Текущее решение
уже удовлетворяет требование «не хардкодить тексты по компонентам».

## Последствия

- Добавление второй локали потребует: обернуть `dict` в провайдер
  выбора словаря (например, по cookie), продублировать
  `ru.ts` → `en.ts`, и заменить прямой импорт `dict` на хук
  `useDict()`. Структура словаря (плоский объект с теми же ключами)
  уже готова для такого перехода.
- Форматирование чисел/дат учитывает локаль явно через
  `Intl.NumberFormat("ru-RU", ...)`/`Intl.DateTimeFormat("ru-RU", ...)`
  (`apps/web/lib/format.ts`), не через словарь — при добавлении локали
  это тоже нужно параметризовать.
