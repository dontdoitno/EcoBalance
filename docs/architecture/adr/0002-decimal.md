# ADR-0002: `Decimal` для внутренней арифметики ядра

- Статус: принято
- Дата: 2026-10-29

## Контекст

ADR-0001 оставил выбор `Decimal` vs типизированный `float` открытым до
начала Этапа 1, когда станет виден объём вычислений и тестовых
golden-кейсов.

## Решение

`ecobalance_core` использует `decimal.Decimal` во всех внутренних
вычислениях (units, scope1/2/3, allocation, engine). Округление до 2
знаков (`ROUND_HALF_UP`) происходит единственный раз — на выходе
`engine.calculate`, не на промежуточных шагах. Pydantic-модели
(`CalculationInput`, `CalculationResult`) используют `Decimal` как
Python-тип; на границе с JSON (FastAPI/`model_dump(mode="json")`) они
сериализуются как строки — фронтенд парсит их явно (`Number(...)`), а
не полагается на автоматическое приведение.

## Почему не `float`

Суммирование большого числа компонентов (топливо + сырьё + энергия +
транспорт + отходы, аллокация, сценарии с несколькими мерами) накопило
бы ошибку округления float, которую сложно отследить в golden-кейсах
(хочется точного равенства в тестах, не `pytest.approx`). `Decimal`
даёт точную воспроизводимость хэндкомпьютед примеров из
`docs/methodology/formulas.md`.

## Последствия

- Все сравнения в тестах (`test_golden_cases.py`) — точное равенство
  `Decimal`, не приближённое.
- Property-тесты (`hypothesis`) используют `st.decimals(..., places=2)`,
  не произвольную точность, чтобы сравнения оставались точными.
- На границе API Decimal → JSON-строка: фронтенд обязан парсить явно
  (см. `apps/web/lib/types.ts` — комментарий о Decimal-как-строке).
